02 Contexte & objectifs

Cadré par la page Confluence « Requirements for Dataset extract – Irrigation coRHYZE » (espace PROD / EDAGRO).

CoRHIZE est un outil de pilotage de l'irrigation. L'objectif est de rendre exploitables les données de sa base pour l'analyse agronomique interne, à partir de la collection Postman fournie par Mathieu A. Trois livrables étaient demandés :

#ObjectifContenu attenduStatut
aListe des parcellesToutes les parcelles, du 01/01/2017 à aujourd'hui, dans un fichier.Livré
bDétails des parcellesMandatory : cultures + dates de semis + surface. Fichier texte et fichier géospatial (gpkg/shp). Should have : tout autre insight.Livré
cDonnées des parcellesMandatory : date + quantité d'eau (irrigation) et date + quantité de précipitations. Fichier texte et géospatial. Should have : toute donnée fournie par l'API.Livré

03 L'API CoRHIZE v2

API REST, authentification par token Bearer. Base : https://portail.corhize.com/api/v2/

EndpointMéthodeRôle
/tokenPOSTAuthentification Basic (user + password) → renvoie token (~24 h) + refresh_token.
/plotsGETListe des parcelles. Chaque parcelle : code, client, lat/long, surface, date de semis, culture.
/plots/{code}GETDétail d'une parcelle + geometry (WKT ou GeoJSON via ?geometry=).
/plots/{code}/dataGETSéries temporelles par data_types (+ bornes from / to).

⚠ Piège rencontré — WAF sur /token

Un POST /token sans corps de requête est rejeté par le pare-feu applicatif (nginx) avec un 403 Forbidden trompeur — qui ressemble à un refus d'authentification alors que les identifiants sont valides. La parade : envoyer un corps de requête (même vide, Content-Length: 0) et un User-Agent classique. Le script gère ça automatiquement.

⚠ Qualité des données à noter

  • Jeu de démonstration / anonymisé : un seul client (CLIENT00308), codes parcelles PLOT000xx, dates de semis en 2026. La profondeur historique réelle observée démarre en 2023, pas 2017.
  • Libellés de culture incohérents : « Maïs semence » coexiste avec « MAIS_SEMENCE », et certains portent un suffixe « * ». Un nettoyage/normalisation est à prévoir avant analyse.
  • 2 géométries invalides sur 243 (WKT non exploitable) — exclues des fichiers géospatiaux, présentes dans les fichiers texte.
  • Should-have absents : ndvi, ET (pet), météo et humidité du sol ne renvoient rien pour ce compte — probablement liés à l'équipement/abonnement des parcelles.

05 Ce que j'ai fait

Un script Python unique, reproductible, qui produit les trois livrables en une passe.

  1. AuthentificationToken Bearer via POST /token (avec contournement WAF), rafraîchi automatiquement en cas d'expiration.
  2. Objectif a — parcellesRécupération des 243 parcelles via GET /plots → plots.csv.
  3. Objectif b — détails + géométriePour chaque parcelle, GET /plots/{code}?geometry=wkt → fichier texte plot_details.csv + conversion WKT → plots.gpkg et plots.shp (EPSG:4326).
  4. Objectif c — séries temporellesPour chaque parcelle, GET /plots/{code}/data (tous data_types) → format long plot_data_long.csv, résumé plot_data_summary.csv, et plot_data.gpkg (polygones + cumuls irrigation/pluie).
  5. RobustesseGestion des géométries invalides, des types de données absents, retries réseau, et identifiants lus depuis l'environnement (aucun secret en dur dans le dépôt).

07 Limites & pistes

→ Recommandations

  • Rejouer sur un compte de production pour couvrir l'historique 2017 et un parc de parcelles multi-clients réel.
  • Normaliser les cultures (table de correspondance) et clarifier la sémantique du suffixe « * » avec CoRHIZE.
  • Confirmer les should-have (ndvi, ET, météo, humidité sol) : disponibles sur d'autres comptes/parcelles ? Le script les captera automatiquement dès qu'ils sont peuplés.
  • Cadence d'irrigation : la granularité est l'apport (événement), idéale pour analyser le pilotage ; on peut dériver des bilans hydriques (irrigation + pluie vs ET) une fois l'ET disponible.
